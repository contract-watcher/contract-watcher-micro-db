### Описание проблемы

На первый взгляд задача MicroDb выглядит довольно просто:

У нас есть набор сущностей, например: `MicroDbSet<User, Guid>`

Мы хотим держать его в памяти, быстро читать данные, иногда изменять их и периодически сохранять состояние в JSON-файл.

И самая очевидная реализация могла бы выглядеть примерно так:

```csharp
private readonly Dictionary<Guid, User> _items = [];
```

Для чтения мы обращаемся к `_items`, для изменения вызываем `Add`, `Remove` или присваиваем новое значение, а при сохранении сериализуем словарь в файл.

Проблемы начинаются в тот момент, когда к одному набору обращаются несколько потоков одновременно. 

### Многопоточность

Когда речь заходит о многопоточности, первое, что обычно приходит в голову, — race condition.

Например:

```csharp
counter++;
```

выглядит как одна операция, но логически состоит как минимум из нескольких действий:

```text
прочитать counter
увеличить значение
записать результат
```

Если два потока одновременно прочитают старое значение, один из результатов может быть потерян.

Например, если `counter` изначально равен `10`:

```text
Поток A                    Поток B

читает 10                  читает 10
увеличивает до 11          увеличивает до 11
записывает 11              записывает 11
```

После выполнения двух операций значение будет равно `11`, хотя ожидаемым результатом является `12`.

Но race condition при выполнении составных операций — только одна часть проблемы.

При работе с общей памятью необходимо учитывать как минимум три свойства:

- **атомарность** — может ли операция наблюдаться или выполняться частично;
- **видимость** — когда изменения, выполненные одним потоком, становятся доступными другому;
- **порядок операций** — в каком порядке чтения и записи могут наблюдаться другими потоками.

Именно последние два пункта часто остаются незаметными, потому что исходный код выглядит последовательным: мы привыкли читать его сверху вниз и предполагаем, что процессор выполняет его точно так же.

В многопоточном коде такого предположения недостаточно.

### Почему исходный порядок кода ещё ничего не гарантирует

Когда мы пишем обычное .NET-приложение, то редко задумываемся, во что в итоге превращается наш `.cs`-файл после компиляции и запуска программы.

Исходный C#-код сначала компилируется в IL, после чего JIT-компилятор преобразует его в машинный код для конкретной архитектуры процессора. На этих этапах, а также непосредственно при выполнении инструкций процессором, могут применяться различные оптимизации, в том числе изменение фактического порядка выполнения отдельных операций.

Делается это, конечно, не для того, чтобы сломать нашу программу. Такие оптимизации позволяют эффективнее использовать процессор, его конвейер, кэши и другие аппаратные возможности.

Для однопоточной программы это обычно остаётся незаметным: несмотря на внутренние преобразования, наблюдаемое поведение программы должно оставаться таким, каким его определяет исходный код.

Проблема появляется тогда, когда в игру вступает несколько потоков и общая память. В таком случае порядок чтений и записей начинает влиять не только на текущий поток, но и на то, какое состояние смогут наблюдать остальные потоки.

Рассмотрим простой пример:

```csharp
private int _value;
private bool _ready;

// Поток A
_value = 42;
_ready = true;

// Поток B
if (_ready)
{
    Console.WriteLine(_value);
}
```

Если смотреть только на исходный код потока A, порядок кажется однозначным:

```text
1. записать 42 в _value
2. записать true в _ready
```

Поэтому естественно ожидать, что если поток B уже увидел `_ready == true`, то он обязательно должен увидеть и `_value == 42`.

Но между этими потоками нет никакой синхронизации, которая гарантировала бы такое наблюдение.

Для потока A его собственное поведение остаётся корректным: внутри него результат выполнения программы не изменился. Однако другой поток не обязан наблюдать записи в том же порядке, в котором они расположены в исходном коде.

То есть нельзя использовать обычную запись:

```csharp
_ready = true;
```

как сигнал:

> «Все предыдущие изменения этого потока теперь гарантированно видны остальным потокам».

Именно в этом месте однопоточная интуиция начинает ломаться: порядок операций внутри одного потока и порядок, в котором результаты этих операций могут наблюдаться другим потоком, — не одно и то же.

### Порядок операций с памятью

В предыдущем примере проблема возникла не потому, что два потока одновременно пытались изменить одно значение.

Поток A выполнял только запись:

```csharp
_value = 42;
_ready = true;
```

а поток B — только чтение:

```csharp
if (_ready)
{
    Console.WriteLine(_value);
}
```

Хорошо, тогда можно попробовать решить проблему проще: дать потоку A немного времени на выполнение перед тем, как поток B начнёт читать данные.

Например:

```csharp
private int _value;
private bool _ready;

// Поток A
_value = 42;
_ready = true;

// Поток B
Thread.Sleep(100);

if (_ready)
{
    Console.WriteLine(_value);
}
```

И на практике такой код вполне может работать. Более того, он может работать тысячу, миллион или вообще все запуски во время разработки.

Но задержка не решает саму проблему — она лишь меняет вероятность того, какой поток и в какой момент получит процессорное время.

Мы по-прежнему никак не описали связь между двумя операциями:

```csharp
_value = 42;
_ready = true;
```

и последующим чтением этих значений другим потоком.

`Thread.Sleep` не является договорённостью вида:

> сначала опубликуй все предыдущие изменения памяти, а только после этого дай другому потоку их прочитать.

Мы всего лишь надеемся, что за отведённое время необходимые операции уже успеют выполниться и стать наблюдаемыми.

Для корректного многопоточного кода такой гарантии недостаточно. Нам нужен механизм, который не зависит от скорости процессора, загруженности системы или удачного расписания потоков, а явно задаёт допустимый порядок операций с памятью.

Для решения таких задач используются барьеры памяти.

Барьер памяти — это ограничение, которое не позволяет определённым операциям чтения и записи свободно перемещаться через заданную точку.

Упрощённо:

```text
записи до барьера
-------------------- memory barrier
операции после барьера
```

То есть вместо надежды:

> «Наверное, к этому моменту предыдущая запись уже видна»

мы задаём правило, которое runtime и процессор должны учитывать при выполнении программы.

При этом барьер памяти сам по себе не означает блокировку потока. Другой поток не обязан останавливаться и ждать освобождения какого-либо ресурса — речь пока идёт именно о порядке и видимости операций с общей памятью.

### Volatile

В .NET для большинства прикладных сценариев нет необходимости самостоятельно расставлять вызовы `Thread.MemoryBarrier()`.

Одним из более удобных инструментов для управления порядком операций с памятью является `Volatile`.

Вернёмся к предыдущему примеру:

```csharp
private int _value;
private bool _ready;

// Поток A
_value = 42;
Volatile.Write(ref _ready, true);

// Поток B
if (Volatile.Read(ref _ready))
{
    Console.WriteLine(_value);
}
```

Здесь `_ready` уже используется не как обычное поле, а как точка публикации состояния.

Сначала поток A изменяет `_value`, а затем выполняет:

```csharp
Volatile.Write(ref _ready, true);
```

Поток B, в свою очередь, получает значение через:

```csharp
Volatile.Read(ref _ready);
```

Эти операции задают необходимые ограничения на порядок работы с памятью.

Упрощённо `Volatile.Write` можно рассматривать как правило:

> предыдущие записи не должны оказаться после этой точки публикации.

А `Volatile.Read`:

> последующие чтения не должны оказаться перед этой точкой.

Таким образом, если поток B наблюдает опубликованное значение `_ready`, мы уже не полагаемся на задержки, скорость процессора или удачный порядок выполнения потоков.

Мы явно задаём правила, по которым состояние публикуется и наблюдается.

Важно при этом понимать, чего `Volatile` **не делает**.

Он не блокирует другие потоки и не запрещает им одновременно выполнять код.

Также он не превращает последовательность из нескольких операций в одну атомарную операцию.

Например:

```csharp
counter++;
```

не станет потокобезопасным только потому, что `counter` читается или записывается через `Volatile`.

Проблема здесь уже не только в порядке операций, а в том, что изменение состоит из нескольких шагов:

```text
прочитать значение
изменить значение
записать результат
```

Для решения такой задачи нужен другой механизм.

### Interlocked

Рассмотрим снова простой пример:

```csharp
counter++;
```

Даже если `counter` читается и записывается с volatile-семантикой, сама операция всё ещё состоит из нескольких шагов:

```text
прочитать значение
увеличить значение
записать результат
```

Поэтому два потока всё ещё могут прочитать одно и то же старое значение и потерять одно из изменений.

Для таких случаев .NET предоставляет класс `Interlocked`, содержащий атомарные операции над общими значениями.

Например:

```csharp
Interlocked.Increment(ref counter);
```

выполняет увеличение значения как одну атомарную операцию.

Более интересным методом является `CompareExchange`.

Его идея выглядит примерно так:

```text
если текущее значение равно ожидаемому:
    заменить его новым значением
иначе:
    оставить всё как есть
```

Причём сравнение и замена выполняются атомарно.

Например:

```csharp
var original = Interlocked.CompareExchange(
    ref value,
    newValue,
    expectedValue);
```

Если `value` всё ещё содержит `expectedValue`, в него будет записано `newValue`.

Если другой поток уже успел изменить `value`, замена не произойдёт.

На основе такой операции можно строить CAS-циклы — алгоритмы, которые повторяют попытку изменения состояния, если другой поток успел изменить его раньше.

### А если одной атомарной операции недостаточно?

`Volatile` позволяет контролировать порядок и видимость операций с памятью.

`Interlocked` позволяет выполнять небольшие атомарные изменения без полноценной блокировки.

Но далеко не любую операцию можно свести к изменению одного значения.

Иногда несколько потоков могут одновременно захотеть выполнить целую последовательность действий, доступ к которой необходимо координировать.

Например:

```text
Поток A → открыть ресурс → изменить → сохранить
Поток B → открыть ресурс → изменить → сохранить
Поток C → открыть ресурс → изменить → сохранить
```

Именно здесь возникает уже более привычный вопрос синхронизации потоков.

### Синхронизация потоков

Когда речь заходит о многопоточности и синхронизации, первое, что можно вспомнить, — уже готовые механизмы, которые предоставляет .NET: `lock`, `Monitor`, `Semaphore`, `SemaphoreSlim`, `Mutex`.

И да, в целом каждый из этих механизмов позволяет тем или иным способом синхронизировать работу потоков. Мы можем ограничить доступ к общему состоянию, не дать нескольким потокам одновременно изменять одни и те же данные и тем самым избавиться от значительной части race condition.

Казалось бы, успех: проблема решена, приложение работает корректно.

Но корректность — это ещё не вся задача.

Можно просто поставить один общий `lock` вокруг всех операций с нашим набором сущностей:

```csharp
lock (_sync)
{
    // чтение
    // изменение
    // сохранение
}
```

Такой код действительно будет гораздо проще рассуждать с точки зрения многопоточности: в каждый момент времени с состоянием работает только один поток.   

Но вместе с этим мы фактически заставляем все операции ждать друг друга, даже если между ними нет реального конфликта.   

Например, обычное чтение сущности из памяти будет вынуждено конкурировать за ту же блокировку, что и изменение состояния. А если в эту же критическую секцию добавить сохранение JSON-файла, то быстрая операция чтения из памяти может начать ждать относительно медленный файловый IO.  

Получается немного странная ситуация: данные уже находятся в RAM и готовы к чтению, но поток всё равно не может получить к ним доступ только потому, что другой поток в этот момент сохраняет их копию на диск.

Получается, нам нужен более точный подход: блокировать только те операции, которые действительно должны выполняться последовательно, и не мешать остальным работать параллельно.

Для этого стоит сначала разобраться, чем вообще отличаются основные механизмы синхронизации, которые предоставляет .NET.

#### `lock` и `Monitor`

Начнём с уже знакомого `lock`.

```csharp
lock (_sync)
{
    DoSomething();
}
```

`lock` предоставляет взаимное исключение: пока один поток выполняет критическую секцию, другой поток, использующий тот же объект синхронизации, будет ждать.

При этом сам `lock` не является отдельным примитивом CLR. По сути это удобный синтаксис C# поверх `Monitor`.

Упрощённо:

```csharp
lock (_sync)
{
    DoSomething();
}
```

можно представить как:

```csharp
Monitor.Enter(_sync);

try
{
    DoSomething();
}
finally
{
    Monitor.Exit(_sync);
}
```

`Monitor` позволяет работать с тем же механизмом более явно и предоставляет дополнительные операции вроде `Wait`, `Pulse` и `PulseAll`.

Но переход от `lock` к `Monitor` не решает нашу исходную проблему.

Если мы защитим всё состояние одним монитором, чтения всё равно будут ждать изменения, а изменения — друг друга.

Можно попробовать использовать несколько блокировок:

```csharp
lock (_readSync)
{
    ...
}

lock (_writeSync)
{
    ...
}
```

или разбить состояние на несколько независимых критических секций.

Это может уменьшить конкуренцию, но одновременно усложняет модель синхронизации.

Как только одна операция начинает требовать несколько блокировок, появляется необходимость соблюдать единый порядок их захвата.

Например:

```csharp
// Поток A
lock (_first)
{
    lock (_second)
    {
        ...
    }
}

// Поток B
lock (_second)
{
    lock (_first)
    {
        ...
    }
}
```

В таком случае поток A может удерживать `_first` и ждать `_second`, пока поток B удерживает `_second` и ждёт `_first`.

Оба потока будут ждать друг друга бесконечно — возникает `deadlock`.

Получается компромисс:

- одна большая блокировка проще, но сильнее ограничивает параллелизм;
- несколько маленьких блокировок уменьшают contention, но усложняют корректную координацию между ними.

#### `Mutex`

Другой механизм взаимного исключения — `Mutex`.

По своей основной идее он похож на `lock`: ресурсом одновременно владеет только один участник.

Но `Mutex` умеет работать не только внутри одного процесса.

Именованный mutex может использоваться для синхронизации нескольких процессов:

```text
Process A ─┐
           ├── Mutex ───> Resource
Process B ─┘
```

Это полезно, если действительно существует общий ресурс, к которому обращаются разные процессы.

Но для обычного доступа нескольких потоков к объекту внутри одного .NET-процесса такая возможность чаще всего избыточна.

`Mutex` использует более тяжёлый механизм операционной системы, тогда как `Monitor`, лежащий в основе `lock`, предназначен именно для эффективной внутрипроцессной синхронизации.

Поэтому заменять обычный `lock` на `Mutex` только ради потокобезопасности внутри одного процесса смысла обычно нет.

#### `Semaphore` и `SemaphoreSlim`

`Semaphore` решает немного другую задачу.

Вместо правила:

> ресурсом может пользоваться только один поток

он позволяет задать количество участников, которые могут одновременно пройти дальше.

Например:

```csharp
var semaphore = new SemaphoreSlim(3);
```

разрешает одновременно выполнять защищённую операцию трём участникам.

Если установить количество разрешений в `1`:

```csharp
var semaphore = new SemaphoreSlim(1, 1);
```

мы получаем поведение, похожее на взаимное исключение: одновременно пройти сможет только одна операция.

Но у `SemaphoreSlim` есть важное для асинхронного кода отличие — `WaitAsync`:

```csharp
await semaphore.WaitAsync();

try
{
    await SaveAsync();
}
finally
{
    semaphore.Release();
}
```

Обычный `lock` нельзя удерживать через `await`.

`SemaphoreSlim`, напротив, позволяет асинхронно ждать доступа к ресурсу, не занимая поток только ради ожидания.

Поэтому он хорошо подходит для координации длительных асинхронных операций, например файлового или сетевого IO.

На этом месте становится заметно, что одной универсальной блокировки для всех операций нам на самом деле не нужно.

У нас есть несколько разных задач:

- чтение уже подготовленного состояния;
- изменение состояния несколькими потоками;
- сохранение состояния в файл.

И требования к ним различаются.

Чтение желательно вообще не блокировать.

Изменения должны корректно конкурировать друг с другом и не терять результаты.

А физическую запись одного файла, наоборот, необходимо выполнять последовательно.

То есть вместо вопроса:

> «Какой один механизм синхронизации выбрать для MicroDb?»

полезнее задать другой:

> «Какой минимальный механизм нужен для каждой конкретной операции?»
